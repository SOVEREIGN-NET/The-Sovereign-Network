# Demo — #2524: POST /api/v1/observer/admission/prepare

## Context — what existed before this PR

The observer admission system (#2523) already has:
- `POST /api/v1/observer/admission/register` — accepts a fully signed
  registration transaction and submits it to the mempool
- `POST /api/v1/observer/admission/challenge` — issues a stateless
  anti-replay nonce
- The executor (`apply_register_observer`) which debits the 1000 nSOV
  registration fee and writes the observer record to sled when a block
  is applied

What was missing: mobile clients had no way to get the canonical bytes
to sign. They would have had to reconstruct the full bincode transaction
format themselves — fragile and platform-dependent.

## What this PR does

Adds the first step of the observer onboarding flow. A mobile client
calls this endpoint to get canonical signing bytes before registering
a new observer node. The server builds the full registration transaction
with a zeroed signature, hashes it deterministically using
`hash_for_signature()`, and returns the 32-byte hash as hex. The client
signs those bytes with Dilithium and passes the signature to
`/admission/register`.

This decouples mobile from bincode — the client never has to reconstruct
the transaction format itself.

## What comes next — #2525

`lib-client/src/observer_admission.rs` — the FFI module that wraps this
endpoint for mobile. It will expose a C-compatible function
`zhtp_observer_admission_prepare()` that calls this endpoint, returns the
canonical bytes to the mobile layer, and handles the Dilithium signing
step so Swift/Kotlin code only passes in keys and DIDs.

## Example request

```
POST /api/v1/observer/admission/prepare
Content-Type: application/json

{
  "observer_node_did":         "did:zhtp:obs-node-abc123",
  "observer_dilithium_pk_hex": "<2592-byte key as hex>",
  "endpoints":                 ["192.168.1.10:9000"],
  "sponsor_user_did":          "did:zhtp:sponsor-user-xyz",
  "sponsor_proof_level":       "Basic",
  "allowed_network":           "mainnet",
  "rate_limit_tier":           "Standard"
}
```

## Example response (200 OK)

```json
{
  "tx_canonical_bytes_hex": "a3f1...c7d2",
  "nonce":                  0,
  "sponsor_next_nonce":     1,
  "chain_id":               3
}
```

`tx_canonical_bytes_hex` is 64 hex characters (32 bytes). The client signs
these bytes with Dilithium and submits them to `/admission/register`.

## Error responses

| Status | Cause |
|--------|-------|
| 400    | Missing required field, invalid hex key, or malformed JSON |
| 403    | Sponsor DID not found on chain |

## Acceptance criteria

- [x] Returns 200 with 64-char hex canonical bytes and correct nonce
      for a valid sponsor DID
      → handler: `observer_admission.rs` `handle_admission_prepare()`

- [x] Full round-trip: prepare → Dilithium sign → `/admission/register`
      → apply block → observer record exists in sled with correct
      sponsor binding
      → test: `prepare_register_round_trip`

- [x] Returns 403 when sponsor DID is not found on chain
      → tested inline in `prepare_register_round_trip` (bad_resp assertion)
