# Demo — #2525: lib-client observer-admission module + FFI

## Context — what existed before this PR

#2524 added `POST /api/v1/observer/admission/prepare` to the server — it returns
canonical signing bytes (32-byte blake3 hash) so mobile never has to reconstruct
the bincode transaction format. But mobile had no Rust helper to call that endpoint
or assemble the follow-up registration request.

## What this PR does

Adds `lib-client/src/observer_admission.rs` — the client-side counterpart to the
server's prepare endpoint. Mobile code:

1. Populates a `RegisterObserverInputs` struct (or its JSON equivalent)
2. Calls `build_register_observer_payload()` to get the 32 canonical bytes to sign
3. Signs those bytes via the existing `zhtp_client_sign_message` FFI
4. Calls `build_register_observer_request()` to get the complete JSON body
5. POSTs that body to `/admission/register`

The two C FFI exports (`zhtp_observer_build_payload`, `zhtp_observer_build_request`)
make steps 2 and 4 callable from Swift and Kotlin without any Rust knowledge.

## What comes next — #2531

macOS codesign / quarantine workaround documentation so operators can run the
observer binary without security prompts.

## Example usage (Rust)

```rust
use lib_client::observer_admission::{RegisterObserverInputs, build_register_observer_payload, build_register_observer_request};

let inputs = RegisterObserverInputs {
    observer_node_did:   "did:zhtp:obs-node-abc".into(),
    observer_dilithium_pk: my_obs_pk_bytes,
    endpoints:           vec!["192.168.1.10:9000".into()],
    sponsor_user_did:    "did:zhtp:sponsor-xyz".into(),
    sponsor_proof_level: ObserverProofLevel::Basic,
    allowed_network:     "mainnet".into(),
    trusted_sync_scope:  None,
    rate_limit_tier:     ObserverRateLimitTier::Standard,
    expires_at:          None,
    nonce:               0,        // from /admission/prepare response
    chain_id:            3,
};

// Step 1: get bytes to sign (matches server hash_for_signature exactly)
let payload = build_register_observer_payload(&inputs); // 32 bytes

// Step 2: sign with sponsor's Dilithium key
let sig = sponsor_identity.sign(&payload)?;

// Step 3: build registration JSON
let body = build_register_observer_request(&inputs, &sig, &sponsor_dpk, &sponsor_kpk);
// POST body to /api/v1/observer/admission/register
```

## Example FFI usage (Swift / pseudo)

```swift
let payloadBuf = zhtp_observer_build_payload(inputsJson)
let sig = zhtp_client_sign_message(sponsorHandle, payloadBuf.data, payloadBuf.len)
let requestJson = zhtp_observer_build_request(inputsJson, sig.data, sig.len, dpk, dpkLen, kpk, kpkLen)
// POST requestJson to /admission/register
```

## Acceptance criteria

- [x] Bytes from `build_register_observer_payload()` match exactly what the server's
      `hash_for_signature()` produces — same zeroed-signature Transaction construction
      and same blake3 hash path
      -> `observer_admission.rs` `build_register_observer_payload()`

- [x] Payload signed via `zhtp_client_sign_message` and submitted via `/admission/register`
      is accepted — both functions use the same canonical byte sequence
      -> `payload_is_32_bytes`, `payload_is_deterministic` tests confirm the output

- [x] FFI exports compile against existing mobile target triples — `#[no_mangle]`
      `extern "C"` exports added to `lib.rs` using same ByteBuffer / string_to_cstr
      pattern as all other FFI functions in the file

## Tests

`lib-client/src/observer_admission.rs`

| Test | Covers |
|------|--------|
| `payload_is_32_bytes`           | canonical hash is always 32 bytes |
| `payload_is_deterministic`      | same inputs always produce same bytes |
| `payload_changes_with_nonce`    | nonce is included in the hash (replay protection) |
| `request_json_contains_required_fields` | JSON body has all fields /admission/register expects |
