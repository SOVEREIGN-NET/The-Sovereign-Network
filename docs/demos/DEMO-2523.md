# Demo — #2523 (T3): zhtp-cli observer subcommand for headless ops

## Context — what existed before this PR

The observer admission system already had server-side was already delivered (#2524):
- `POST /api/v1/observer/admission/prepare` — returns canonical signing bytes
- `POST /api/v1/observer/admission/register` — submits signed registration tx
- `GET /api/v1/observer/admission/status?did=...` — poll admission status
- `GET /api/v1/observer/admission/by-sponsor?did=...` — list sponsor's observers
- The executor + sled persistence

What was missing: **the operator-facing CLI** that a headless operator (or desktop user) uses to interact with these endpoints. The existing `zhtp-cli` binary had no observer-related commands at all.

## What this PR does

Adds a top-level `zhtp-cli observer` subcommand with 7 subcommands for interacting with the observer admission system **without** the web UI. This lives on the existing `zhtp-cli` binary only — NOT on the `zhtp-observer` daemon (T6).

All 7 subcommands are wired into the standard clap argument parsing framework alongside `wallet`, `dao`, `oracle`, `nft`, etc.

## Subcommands

| Command | What it does | Network needed |
|---------|--------------|----------------|
| `observer generate` | Create Dilithium5+Kyber1024 keypair, save to `~/.zhtp/keystore/observer/` | No |
| `observer qr-payload --did <did>` | POST to `/prepare`, print JSON payload for mobile | Yes (node) |
| `observer qr-render --did <did>` | Same payload rendered as ASCII QR in terminal | Yes (node) |
| `observer status --did <did>` | GET `/admission/status`, print JSON + status summary | Yes (node) |
| `observer wait --did> --timeout 300` | Poll status every 2s until Active or timeout | Yes (node) |
| `observer start --did <did>` | Spawn observer node once admitted | Yes (node) |
| `observer by-sponsor --did <did>` | GET `/admission/by-sponsor`, list sponsor's observers | Yes (node) |

## Architecture

```
┌─────────────────────────────────────────────────────┐
│                 zhtp-cli observer                    │
│                                                      │
│  argument_parsing.rs                                 │
│  └─ ZhtpCommand::Observer(ObserverArgs)              │
│      └─ ObserverAction enum (7 variants)             │
│           ├─ Generate                                │
│           ├─ QrPayload  { did: String }              │
│           ├─ QrRender   { did: String }              │
│           ├─ Status     { did: String }              │
│           ├─ Wait       { did: String, timeout: u64 }│
│           ├─ Start      { did: String }              │
│           └─ BySponsor  { did: String }              │
│                                                      │
│  commands/observer.rs                                │
│  └─ handle_observer_command(args, cli) → dispatch    │
│      ├─ cmd_generate()    — ZhtpIdentity::new_unified│
│      ├─ cmd_qr_payload()  — POST /prepare           │
│      ├─ cmd_qr_render()   — POST /prepare + QR code │
│      ├─ cmd_status()      — GET /admission/status   │
│      ├─ cmd_wait()        — poll loop               │
│      ├─ cmd_start()       — spawn observer process  │
│      └─ cmd_by_sponsor()  — GET /admission/by-sponsor│
└─────────────────────────────────────────────────────┘
```

## Key design decisions

1. **ObserverAction enum moved to `argument_parsing.rs`** — follows existing convention (`NftAction`, `TokenAction`, `CurveAction`). Clap derive lives alongside all other command definitions.

2. **Observer keystore isolated to `~/.zhtp/keystore/observer/`** — never touches `~/.zhtp/keystore/` (user identity). The epic mandates "the desktop never holds a user identity."

3. **Keypair uses `ZhtpIdentity::new_unified()`** — Dilithium5+Kyber1024 via the non-legacy path (no Ed25519, no deprecated `KeyPair::generate()`).

4. **`connect_default()` for read-only queries** — `status`, `wait`, `by-sponsor`, `start` use the default identity for QUIC handshake. `qr-payload`/`qr-render` use the observer identity since they need the observer's public key.

## Example usage

**Generate identity:**
```
$ zhtp-cli observer generate

Generate Observer Identity
==========================
Observer identity generated successfully!
  DID:                did:zhtp:31eb2d60b195f7ca6c025c9dbab6b700fad6a7ca505d4ded78af7fd92bb26ebb
  Dilithium PK (hex): 4222ed68...
  Kyber PK (hex):     b3b422f0...
  Keystore:           /home/user/.zhtp/keystore/observer/
```

**Query status against testnet:**
```
$ zhtp-cli --server 77.42.37.161:9334 observer status \
    --did did:zhtp:31eb2d60b195f7ca6c025c9dbab6b700fad6a7ca505d4ded78af7fd92bb26ebb

{
  "record": null,
  "status": "ok"
}
```

**Wait with timeout:**
```
$ zhtp-cli --server 77.42.37.161:9334 observer wait \
    --did did:zhtp:31eb2d60b195f7ca6c025c9dbab6b700fad6a7ca505d4ded78af7fd92bb26ebb \
    --timeout 10

Waiting for observer did:zhtp:31eb... to become Active (timeout: 10s)...
No record yet — polling again in 2s (7s remaining)...
No record yet — polling again in 2s (4s remaining)...
No record yet — polling again in 2s (1s remaining)...
Error: Timeout after 10s
```

**Error paths:**
```
$ zhtp-cli observer qr-render --did did:zhtp:no-such-did
Error: Configuration error: Observer keystore not found at ...
Run 'zhtp-cli observer generate' first.

$ zhtp-cli --server 77.42.37.161:9334 observer start \
    --did did:zhtp:31eb2d60b195f7ca6c025c9dbab6b700fad6a7ca505d4ded78af7fd92bb26ebb
Error: Configuration error: Observer ... has no admission record on chain.
Complete the QR enrollment flow first.
```
